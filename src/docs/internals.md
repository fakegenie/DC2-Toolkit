# How the tools work

How the code is organised, how data goes from the disc to editable files
and back, and how the decompiler and compiler work. How to change the code
(the checks, the conventions, the golden snapshot) is in
[development](development.md); why it is built this way, in [design](design.md).

## The crates

A Cargo workspace (`src/Cargo.toml`, the crates in `src/crates/`),
each crate depending only on the ones above it:

| crate | depends on | holds |
|---|---|---|
| `dc2tk-disc` | | the disc image, `DATA.HD4`/`DATA.DAT`, packs, extracting and writing a disc |
| `dc2tk-assets` | `dc2tk-disc` | the game's file formats, converted to common formats and back; the data tables; the asset tree |
| `dc2tk-script` | `dc2tk-disc`, `dc2tk-assets` | the scripts: `.stb`, the VM, the C language, decompiling and compiling; mods and `build`'s stages |
| `dc2tk` | all three | the command line |

The libraries do the work. The binary parses the arguments, calls a
library's stage and prints what it did; a stage that used to live in it
(the data tables, the item messages, a mod's maps, decompiling a whole
disc) is now a library function a test can call. Every module starts with
a doc comment saying what it is for, so what follows is a map, not a
description.

### dc2tk-disc

- `iso`: ISO 9660 directory records. `archive`: `DATA.HD4`, the index of
  `DATA.DAT` (`parse_index`, `Entry`; the engine reads it into a buffer of
  `INDEX_LIMIT`, 0x50000 bytes, and a build that would pass it is refused), and the packs (`.chr`, `.snd`, `.mpk`, ...)
  that chain members in 0x50-byte slots: `parse_pack` gives the `Member`s,
  and `Pack` is a pack read whole, keeping the slot bytes the game never
  reads, so that `Pack::write` gives it back byte for byte.
- `extract`: every file of `DATA.DAT`, and every member of its packs (four
  deep, `MAX_PACK_DEPTH`), as a folder: a pack `X` keeps its bytes as `X`
  and its members under `X.d/`. `manifest.json` (`extract::Manifest`, not to
  be confused with the asset tree's) lists them and is written last, so it
  marks a finished extraction. A file is unpacked only when it matches every
  rule of a pack ([the disc](../../docs/internals/disc.md#pack-files): each entry's
  data at 0x50, `next` rounded up to 16, an empty last entry): a looser check
  unpacked 587 scripts by mistake, because a script's header and program
  table can read as one pack entry named `SB2`. `layout` keeps the disc's other files and
  what no file holds (`disc.json`, `disc-structure.bin`), so `layout::pack`
  writes the folder back into the retail image.
- `source`: `DiscSource`, the disc's files by `DATA.DAT` path from either
  form a disc takes: the image (mapped, read without copying) or an
  extracted disc. Every command that takes "the disc image or an extracted
  disc" opens one; the game's paths ignore case, and so does it.
- `rebuild`: changing the disc. `replaced_member` and `added_member` change
  a member deep in packs; `write_disc` writes a new image with `DATA.DAT`
  files replaced or added (a file that still fits its sectors stays, one
  that grows moves into the `DMMY` filler and then past the end of the
  volume, new files get index records), and refuses an output that is its
  input; `overwrite_iso_file` patches a file outside `DATA.DAT` (the boot
  executable) in place, at its size.
- `text`: cp932 names, encoding_rs's Shift_JIS with the corrections of
  `cp932_fixes` (generated by `examples/cp932_fixes.rs`). `textfile`: the
  text files the tools write. `files`: `std::fs` with errors that name the
  file.
- `samples`: small discs, indexes, packs and a script built in memory, for
  tests (this crate's, and the others' through the `test-support` feature
  of their dev-dependencies).

### dc2tk-assets

`lib.rs` groups the modules:

- binary formats, read and written byte for byte: `bytes` (little-endian
  reads at an offset, `u32_at` and the like, and the `Reader` cursor, every
  read bounds-checked), `im3` (texture files of TIM2 pictures), `png`,
  `mds` (models), `mot` (`.mot` motions, `.wgt` weights, `.bbp` bind poses),
  `sequence` (`.sq`), `soundbank` (`.snd`), `font`;
- glTF: `to_gltf` and `from_gltf` (characters), `models` (a character pack
  as a glTF folder, and a new pack from a glTF), `motions`, `gltf`
  (accessor types), `math` (column-major `Mat4`, quaternions); maps:
  `mapfile` (the `.map` file as a typed tree), `map_scene`, `map_export`,
  `map_import`, `map_edit`, `map_transform`, `map_display` (what a scene only
  shows: the sky by time band, the `.cfg`'s water, occlusion planes, hidden
  areas, extra trigger points and villagers);
- textures and sounds for mods: `textures`, `quantise` (median cut),
  `sounds` (WAVs), `music` (MIDI), `soundfont`;
- data tables and text: `cfg_text` (a cfg script kept whole, so one
  argument changes and the rest writes back exactly), `data_table` (the
  engine every table is built on: named records whose fields are cfg
  arguments or bytes of the executable, a mod's JSON turned into cfg edits
  and `elf::Patch`es), `game_data` (the kinds by their `data:` name),
  `item_data`, `shop_data`, `monster_data`, `exe_tables`,
  `invention_data`, `idea_data`, `georama_data`, `town_data`,
  `dungeon_data`, `dungeon_layout`, `chest_data`, `fishing_data`; `elf` (the
  boot executable `SCES_511.90`: where a vaddr is in the file, patches in
  place), `lang` (languages as the tables keep them), `json` (the tables'
  JSON, and errors naming a member of the wrong shape), `info_cfg`, `text`
  (message files);
- the asset tree: `tree` (`tree::build`, and `tree::named`, the walk and
  naming the index shares), `manifest` (the tree's `manifest.json` as
  types), `ids` (`Index`, the ids and their places, from the disc or from a
  manifest), `tree_check`, `folder` (files in memory, named as the file
  system names them), `numeric` (the arithmetic the converters' bytes
  depend on);
- `malformed` (tests only): the malformed-input sweep.

### dc2tk-script

`lib.rs` groups the modules by area; those only the crate uses are
`pub(crate)`.

- The program tree, `.stb` and its assembly, the native tables, the test
  VM: `node` (`Node`), `stb` (the opcodes, addressing modes and comparisons
  of [the script format](../../docs/internals/scripts.md), defined once as
  `stb::Op`, `stb::Mode` and `stb::Compare` for every part of the tools),
  `asm`, `fingerprint`, `natives` (the tables in `definitions/natives/*.json`, and
  `table_for`, which picks a script's table by its path), `stack` (stack
  effects, walked back from an `EXT` to find the native number; the natives
  stage folds a group base plus offset before looking the number up), `vm`.
- The C-like language: `parse/` (`lex`, the tokenizer and preprocessor;
  `program`, file scope; `declarations`, `types`, `statements`,
  `expressions`), `cpp` (macros and `#if`), `ctype` (C's types beyond the
  VM's scalars), `lower` and `composite` (standard C lowered to what the VM
  has), `sdk/` (`headers` loads the SDK, `resolve` compiles through it,
  `present` decompiles through it, `reference` writes the API pages of
  `docs/scripting/api/` for `dc2tk api-docs`), `compile`, `source` (the C
  writer).
- Decompiling a disc: `decompile`, `decompiler`, `definitions`, `names`,
  `library`, `messages`, `notes`, `disc` (`disc.h`), `assets` (the asset
  names' `#define`s), `slots`, `slotflow`, `villagers`, `soundpass`,
  `learn` and `coverage` (`defs learn`, `defs check`).
- A decompiled tree read as text, for the commands that answer questions
  about it: `index`, `flags`, `xref`, `maps`, `loads`, `constants`,
  `pathnames` (readable names and the `UNNAMED` record), `tree` (the record
  of what the decompiler wrote, which tells edits from its output).
- Mods and building: `mods` (mod folders, whole files, choosing mods by
  id), `manifest` (`mod.json` and `mod.lock` as typed records, `mod
  upgrade`), `semver` (versions and ranges), `patches` (`#pragma target`), `additions`, `numbers` (`NEW_FLAG` and its
  kin, kept in the lock file), `slim`, `capture`
  (`diff`, `mod make`), `editor`, `replace` (assets by id), `discfiles`
  (`disc/` and `file:`), `datatables` and `itemtext`, `mapedit`,
  `mapscript`, `maptable`, `startat`, `build` (which scripts can have
  changed), `memory/` (the memory budgets).
- `paths`: paths as the tools write them, and walking folders.

The native tables: `dc2tk natives <chronicletwo>` reads each table of the
decomp and its enum and writes `definitions/natives/<table>.json` (checked in) as
`{no, name, accessors}` rows. `accessors` lists the stack calls in the
native's body in source order (`int`, `float`, `string`, `vector`, `any`,
`out`, `out_vector`). It is a hint for argument types, not a signature:
bodies index the stack in loops and branches. The decompiler does not need
it, because the bytecode already shows `&x` (`LOAD_ADDR`) and each
constant's type.

### dc2tk

`main.rs` holds the command enum and the small commands; `options.rs` the
options commands share (`Common`: definition sets, `--no-defs`, native
tables; `ModsDir`; `Tools`, what compiling needs, loaded once); `files.rs`
where the data folders are. Then one module per group of commands:
`setup.rs` (`setup`, `natives`), `modding/` (`build.rs`, `check.rs` for
`mod check`, `pcsx2.rs` for `play` and `--play`, the other mod commands in
`mod.rs`), `verify.rs`, `defs.rs`, `xref.rs` (`xref`, `maps`, `map`),
`asset_tree.rs` (`assets` and the hidden `assets-check`), `map_cmd.rs`
(`map-export`). The binary's errors are `anyhow`'s, printed whole with
their causes; any error exits with 1.

## From the disc to files and back

1. **Extract.** `extract::extract` writes the image's files into
   `extracted/disc/` (`dc2tk extract`, `setup`); `layout::pack` writes the
   folder back, the retail image when nothing changed (`dc2tk pack --check`
   compares them).
2. **Decompile.** `decompiler::decompile_tree` turns the extracted disc into
   `extracted/scripts/` (`decompile`, `setup`): each script's functions are
   fingerprinted, the shared ones cut into libraries (`library::model_for`),
   each script decompiled, named and presented, and written as C, with
   `include/disc.h` (names read from the disc), `compile_flags.txt` for
   editors, and the tree's records (`tree`, `pathnames`).
3. **The asset tree.** `tree::build` writes every texture, model, sound,
   text and music asset once into `extracted/assets/`, with its manifest
   (`dc2tk assets`, `setup`). Maps and data tables are beside it, not in
   it: `map_cmd::export_all` writes every map as a glTF scene into
   `extracted/maps/` (`setup`, or `dc2tk map-export --all`; one map,
   `map-export NAME`), and `datatables::export_all` every data table as
   JSON into `extracted/data/` (`setup`; `mod asset ... data:items` copies
   one into a mod).
4. **Mods** are folders over the tree: patches, whole files, and
   `mod.json`'s lines by asset id, path, map and table.
5. **Build** (`dc2tk/src/modding/build.rs`, each step a library call):
   - plan: the mods' files overlaid on the tree (`mods::overlay`), their
     `disc/` files (`discfiles::collect`), their ids resolved against the
     disc's index (`replace`, `ids::Index::from_disc`), clashes refused, the
     patches planned and their numbers given (`patches`, `numbers`);
     `--start-at`'s patch of the new-game script (`startat`);
   - compile: every script that can differ from the disc compiled and
     compared with it (`build::changes`);
   - game files, each step over the files the steps before wrote: `disc/`
     and `file:` files (`discfiles::replaced`); the id lines
     (`replace::apply_with`: models, then banks, then pictures, then texts
     and music); new music files (`replace::add_music`); maps
     (`mapedit::apply_maps`, new maps' scripts by `mapscript`, their rows by
     `maptable`); the data tables (`datatables::apply_data`);
   - the memory check over the loads those files change (`memory::check`);
   - the image (`rebuild::write_disc`), then the executable's patches
     (`rebuild::overwrite_iso_file`);
   - every changed script and file read back from the new image and
     compared with what was meant (`read_back`).

## Libraries

The 144,202 functions on the disc have only 10,789 distinct bodies. The
original scripts pulled in shared source files, and each compiled script
carries its own copy of everything it included, so most of a script is
library code. Recovering those libraries is what makes the decompiled source
readable.

A function's identity is its fingerprint: a hash of its bytecode (without
its name or string padding) and the fingerprints of the functions it calls,
plus the native table (see
[how definitions find things](../../definitions/README.md#how-definitions-find-things)). No script calls a later function or
itself, so fingerprints are well defined and the same in every file.
`fingerprint.rs` hashes a compact JSON payload (the native table, the
argument and local counts, `arg_types`, the unused strings, and the
instructions with jumps relative to the function, calls by the callee's
fingerprint and pushed strings by their text) and keeps the first 16 hex
digits of its SHA-1. The payload is written out by hand, not by a JSON
library, so the fingerprints stored in definitions and mods keep matching.
The loose fingerprint leaves the strings' text out: it finds the same
function in another language's script.

`src/crates/dc2tk-script/src/library.rs` finds the libraries over the whole disc:

1. A function can join a library when it is the first copy of its body in
   the file and everything it calls can too.
2. Each script is cut greedily from the start into the longest runs of
   functions that appear, in order, in at least one other script.
3. Every distinct run used by two or more scripts becomes a library file,
   placed under `lib/` in the deepest folder all its users share
   (`lib/map/s/s05/s05_12.c`, given the folder's readable name,
   `s05_fish_monster_swamp`, and usually a better name from
   `libraries.json`). Runs only one script uses stay inline.

The libraries evolved while the game was made, so the same helper exists in
several versions and a library file is one exact version. The disc gives
1,097 library files. The median script includes three of them and keeps
about one function of its own; the scripts shrink from 3.9 million lines to
587,000.

The compiler expands each `#include` in place, so the bytes do not change.
Library files carry no padding pragmas; a block the buffer rules do not
give would be listed by the script, for its own and its included functions,
with `#pragma padding_of NAME HEX` at the end of the file.

## Names

Retail scripts keep no names, so every name in the source is chosen.
`definitions/pal/names/<table>.json` maps fingerprints to a function name and,
optionally, parameter and local names:

```json
{"functions": {"3f9a...": {"name": "wait_frames", "loose": "d74d...", "params": ["frames"], "doc": "..."}}}
```

A function is found by its exact fingerprint, else by the loose one
(`names.rs`), so a translated script gets the names too.

Because the key is the fingerprint, one entry names that function in every
script and library that has it. Two versions of a helper can share a name;
when two such versions would meet in one file, the later one gets a numbered
suffix (`swing_attack_2`). A later copy of code the file already holds is
named for its one caller (`unlock_interrupts_for_recoil_from_hit`) or as
unused (`unused_do_nothing`). Variable names that would clash with each other or with a
global are ignored.

Every function on the disc now has a name. Names are checked by `verify`
like everything else, since a wrong name can only make the source less
clear, never change the bytes.

Functions without an entry get defaults: library functions are named after
the library that first holds them and their position in it (`map_2_40`),
entry points `on_` plus their program's name (`on_map_start`), or
`program_100` when the program has no name, the header's main
function `start`, and the rest `func_1`, `func_2` in file order. Variables
default to their slot: `a0` for arguments, `v3` for locals, `g1` for
globals.

## Decompiler

`decompile.rs` (in `src/crates/dc2tk-script/src/`) turns a script `stb::read`
gave into a program tree (`Node`, `node.rs`: ordered maps and lists that
dump as JSON, their kinds named in `node::kinds`); `names.rs` names it from
the definition set, `messages.rs` and `notes.rs` put the game's text beside
the calls, `sdk/present.rs` presents it with the SDK's names and helpers
(`sdk/headers.rs` loads the headers, `sdk/resolve.rs` resolves the other way
when compiling), and `source.rs` prints it as C. `decompiler.rs` runs them
with the definitions, reading what does not change between scripts once
(`Setup`), for one script (`script_source`) or a whole extracted disc
written as a source tree (`decompile_tree`, which `dc2tk decompile` and
`setup` print the result of).

The `.stb` reader never fails: what it cannot place is kept as raw regions,
so every file reads and writes back unchanged (`stb::Region`). The
instructions are `stb::Op`, their addressing modes `stb::Mode` (a `Place`,
local, local array, through a pointer or global, and whether the value is
read as a float), each defined once with its number and its assembly name.

1. Declarations come from the addressing modes: each slot is used with one
   mode, so it is an `int` or `float` scalar, a local array (indexed modes, the
   size running to the next used slot) or an array parameter (pointer modes).
   The declared `arg_types` must agree.
2. Expressions are rebuilt by simulating the stack until a statement-ending
   instruction (`POP`, `RET`, `EXT`, `PRINT`, `WAIT`, `END`, `SKIP_END` or a
   jump).
3. Control flow follows the compiler's fixed shapes. Every jump target is a
   `NOP` whose `arg1` is a label number, allocated per function in the order
   the compiler met them: `while` takes its top and exit labels before its
   condition, `if` takes its else label after the condition and its end label
   after the then-block, and `&&`/`||` (`jf_push`/`jt_push`) take theirs after
   the left operand. The decompiler checks the numbers come out in that order,
   so the compiler can reproduce them by counting.
4. A function must end in `push 0; ret`, the compiler's implicit return.
   Anything outside these shapes makes the function an `asm` block.

## Compiler

`parse/` reads `.c` into the same tree (`parse/lex.rs` tokenizes and preprocesses, the
other parts parse file scope, declarations, types, statements and expressions) and `compile.rs` turns
the tree into text assembly, which `asm::assemble` lays out. Slots, label
numbers, native numbers and string indices are assigned by the rules above;
the assembler computes every offset, record field and header field.

`compile::compile_file` runs the whole way: the included libraries' texts
are read (`library::include_texts`), the file parsed with them
(`parse::parse_with` and its `ParseOptions`; `parse::parse` for a text
alone), the includes expanded in place (`library::expand`), the native
table chosen (`#pragma natives`, else by the script's path), and
`compile_program` resolves the tree (`sdk::resolve`: initialised globals
(`lower::initialised_globals`), then C's pointers and composite types
(`composite::lower`), then the narrow integer types (`lower::integer_types`),
then helpers expanded and natives and constants resolved), writes it as
assembly (`compile::to_asm`) and assembles it. The forms the decompiler
writes pass through the lowering unchanged, so retail scripts keep their
bytes; only new code takes the other paths ([the C standard](c-standard.md)).

String blocks hold the function's strings in push order, padded to 16 bytes
with whatever the compiler's string buffer held there from earlier blocks
(`stb::block_padding`), and the code section ends zero-filled to 16
(`stb::tail_padding`, the assembler's `.tail`). In the 55 files marked
`#pragma string_pool` the buffer was never reset, so each block starts with
the file's strings so far and a function with no strings writes them all
(`stb::pool_block`). The decompiler tries both and keeps the one that
predicts every block; together they give every block on the PAL disc, so no
`#pragma padding_of` or `#pragma strings` lines are printed. They are still
read, and printed for a block neither rule gives.

## Errors

Each library has its own `Error` (`thiserror`) and `Result`:

- `dc2tk_disc::Error`: `Invalid` (data that is not what it should be),
  `NotIso`, `Missing` (a file the disc must have), `File` (a file that
  could not be read or written, with its path and the cause in one
  message: "cannot read PATH: CAUSE") and `Io`. `dc2tk_disc::files` wraps
  `std::fs` so every read and write in the workspace can name its file;
  among the thousands a build reads, a bare "os error 2" says nothing.
- `dc2tk_assets::Error`: `Invalid` and `Io`; the disc's errors convert, a
  missing or unreadable file becoming `Invalid` with its message. Its
  `Context` trait (`.context("track 3")`) puts what was being read in
  front of any error that displays, so a failure deep in a file names the
  file, the record and the field. `bail!` returns an `Invalid`.
- `dc2tk_script::Error`: `Invalid`; `At`, an error of a source statement
  with its line (`Error::at` gives the innermost statement's line);
  `Context`, an error with what was being done (`texture:tex02 (mod
  fish): ...`, from its own `Context` trait), which keeps its cause; `Io`
  and `Disc`. `is_input` tells an error of the input (a source file, a
  tree, a mod) from one of reading or writing.

Malformed input, from the disc, a mod or a hand-edited file, is an error,
never a panic: the readers check every offset and count (`bytes`, checked
arithmetic), sizes are checked before anything is allocated, and a JSON
value of the wrong shape or range is refused naming the member rather than
dropped or truncated. Two mods giving one thing different values are
refused with one message, "... is given two ways, by mod A and mod B".

## What must not change, and the limits

The one hard rule: an image the tools build is the retail image wherever
nothing was edited. So an unedited extracted disc packs to the retail
bytes, an unedited tree compiles to the disc's scripts, every asset and
data table written back unedited gives its game file's bytes, and a build
writes only the files it changed (an unchanged file keeps its sectors, the
executable is patched in place at its size, a table changes only the bytes
of the fields a mod changes). Everything else (the text of the C, JSON,
reports and messages) may change when the change is deliberate. The text
files the tools write go through `dc2tk_disc::textfile`: UTF-8, `\n` line
endings, JSON as serde_json's pretty form (two-space indent) with a final
newline; reading takes `\r\n` too. Game files never go through it.

The limits are named constants:

| limit | value | what it stops |
|---|---|---|
| `parse::NESTING` | 200 | nesting deeper than a 1 MB stack holds in a debug build (parentheses 64 deep, statements 97, an operator chain 194 long): "nested too deeply", not a crash |
| `vm::STEPS` | 10,000,000 instructions | a test that loops for ever |
| `vm::CALLS` | 10,000 nested calls | a test that recurses without end (the VM's calls are its own, so Rust's stack is never at risk) |
| `archive::INDEX_LIMIT` | 0x50000 bytes | the engine's buffer for `DATA.HD4`: a new file costs its path and 13 bytes, and `build` refuses more ("put new files into packs instead") and prints the room left |
| `extract::MAX_PACK_DEPTH` | 4 | how deep extract and the asset tree go into packs |
| `flags::FLAG_COUNT`, `COUNTER_COUNT` | 2,048 flags, 128 counters | the save's |
| `maptable::FLAGGED_MAPS` | 256 | a new map numbered past it loads but keeps no map flags |
| `replace::MAP_NAME_MOST` | 12 | a new map's name, in the engine's 32-byte file names |

An integer literal past 32 bits is an error. The memory budgets the build
checks (`memory/`, `READ_BUFFER`, the measured `RETAIL_*` maps) are in
[memory](assets/memory.md).

## Tests

- Unit tests beside the code (`#[cfg(test)] mod tests`), and integration
  tests in `src/crates/dc2tk-script/tests/` (`common/` and `build_common/`
  hold what they share), on small discs, packs and scripts built in memory
  (`dc2tk_disc::samples`). Nothing needs the game's files.
- The C89 suite: a program in `tests/c89/` for each feature of the
  language, compiled and run in the test VM, its second line
  saying what it shows (`// expect:`, `// rejects:`, `// differs:`,
  `// planned:`, `// limit:`); [the C standard](c-standard.md) lists them.
- `tests/nesting.rs`: the whole compile at `parse::NESTING`, on a thread
  with a 1 MB stack. `dc2tk-assets`' `malformed.rs`: a small file of each
  binary format cut at every length and with bytes changed at every place,
  read without a panic.
- The corpus tests read an extracted retail disc and are
  `#[ignore = "needs DC2TK_CORPUS"]`: `DC2TK_CORPUS=/abs/path/extracted/disc
  cargo test --release --workspace -- --include-ignored` runs them, and
  `samples::corpus()` fails them loudly when the variable is unset. They
  round-trip the whole disc's scripts (`verify`'s, about 40 s), every
  `.map`, `.sq` and message file, every data table, the asset tree against
  the index, and the memory budgets against the retail measurements.
- The golden snapshot (`tools/golden.sh`, in [development](development.md))
  checks the binary's whole output, and that every image it builds is
  unchanged.

# Code style

- Rust, one Cargo workspace (`src/Cargo.toml`, crates in `src/crates/`;
  see [its README](../README.md)), formatted with `cargo fmt`
  (`rustfmt.toml`: 120 columns), clean under `cargo clippy -- -D warnings`,
  with few dependencies.
- Functions and plain data: structs for fixed records (the `.stb` header,
  instructions, functions), and few traits or wrappers. Kinds of value are
  enums, not strings (`stb::Op`, `stb::Mode`, `numbers::NumberKind`,
  `patches::TargetKind`, `replace::LineKind`, `soundpass::PortValue`,
  `map_export::PackType`), and the program tree's node kinds are the
  `node::kinds` constants. One reader per format: `maptable::rows` for the
  map tables, `archive::Pack` for packs, `DiscSource` for "an image or an
  extracted disc", `bytes` for little-endian values.
- Each module starts with a doc comment saying what it is for; comments
  inside functions are rare. If code needs one, it may need to be simpler.
  Comments say why, citing the engine's function and source file a
  behaviour comes from. Long work is split into named steps: no function
  is over clippy's 100 lines.
- Intermediate forms (parsed file, instruction lists, syntax trees) are
  plain data that can be dumped as JSON (`Node` for the program tree), which
  makes every stage inspectable.
- Regexes are `LazyLock` statics, compiled once.
- Work over many files runs on every core (`rayon`); the results come out
  in a fixed order, so the same input always gives the same output.
